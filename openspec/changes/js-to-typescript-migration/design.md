## Context

The library has 27 remaining JS/JSX source files alongside 54 already-converted TS/TSX files. The JS files fall into distinct categories:

1. **Class components with `prop-types`** (12 files): `sharing/` JSX components, `org-unit-select/` components, `group-editor/` components, `OrgUnitsSelector.jsx`, `DialogButton.jsx`, `SimpleCheckBox.js`. These use `PropTypes`, class state, `.bind(this)`, and legacy `contextTypes`.
2. **Utility modules** (7 files): `utils/lodash.js`, `utils/date.js`, `utils/d2-auth.js`, `helpers/d2.js`, `sharing/utils.js`, `org-unit-select/common.js`, `org-unit-tree/utils.js`. Pure functions, easier to type.
3. **Barrel re-exports** (4 files, 1 excluded): `auth/index.js`, `org-unit-select/index.js`, `group-editor/index.js`, `org-unit-tree/index.js`. Trivial to rename. (`locales/index.js` is auto-generated by `d2-i18n-generate` and excluded from migration.)
4. **Tree components** (3 files): `org-unit-tree/` — class components wrapping `@dhis2/ui` OrgUnitTree.

The `d2` DHIS2 library is used via React `contextTypes` (a legacy pattern) in the `org-unit-select` components. Its types are loose — `api.models`, `api.get()`, etc. are untyped.

## Goals / Non-Goals

**Goals:**
- Convert all 27 JS/JSX files to TS/TSX with proper type annotations.
- Replace all `prop-types` with TypeScript interfaces.
- Maintain identical runtime behavior and public API surface.
- Clean up build config after migration (`allowJs`, `babel-jest` transform).

**Non-Goals:**
- Refactoring class components to functional components (separate effort).
- Creating comprehensive type definitions for the `d2` library.
- Changing component behavior or public APIs.
- Removing `loglevel`, `lodash`, or other runtime dependencies.

## Decisions

### 1. Convert in dependency order (leaves first)

Convert files bottom-up: utilities and barrels first, then components that depend on them. This ensures each converted file can import already-typed modules.

**Order:** barrels/indexes -> utilities -> org-unit-tree -> org-unit-select -> sharing -> group-editor -> remaining components -> config cleanup.

**Why over top-down:** Bottom-up means each file we touch already has typed imports, reducing `any` usage and avoiding forward-reference type issues.

### 2. Use `any` sparingly for `d2` API interop

The `d2` library's `api` object (accessed via legacy `contextTypes`) lacks type definitions. We will define a minimal `D2Api` interface in `src/types/d2-ui.d.ts` (which already exists) covering the methods actually used: `api.get()`, `api.models.organisationUnits`, etc.

**Why not full d2 types:** The library is a peer dependency and its types are out of our control. Typing only what we use keeps the scope bounded.

**Why not just `any` everywhere:** A thin interface still catches typos and documents the API surface we depend on.

### 3. Keep class components as-is

The JSX class components (UserSearch, PermissionPicker, etc.) will be converted to `.tsx` with typed props/state interfaces but will remain as class components. Converting to functional components is a separate behavioral refactor.

**Why:** Minimizes risk. Class-to-function conversion changes lifecycle behavior and is out of scope for a type-only migration.

### 4. Replace `contextTypes` with typed approach

The `org-unit-select` components use `static contextTypes = { api: PropTypes.any }`. We'll replace this with a properly typed context pattern — either a typed `contextType` static property or accepting `api` as a prop, depending on what existing TS components in the codebase already do.

### 5. Config cleanup as final step

Only after all files are converted and tests pass:
- Remove `allowJs: true` from `tsconfig.json`
- Simplify `jest.config.js` to drop `babel-jest` JS transform
- Remove `prop-types` from `devDependencies`
- Convert `setupEnzyme.js` to `.ts`

**Why last:** Keeps the migration incrementally testable — each batch of conversions can be verified with `yarn build && yarn test` before the next.

## Risks / Trade-offs

- **[Risk] `d2` API types may be incomplete** -> Mitigation: Use a thin `D2Api` interface covering only methods actually called. Allow targeted `any` for deeply nested `d2` return types.
- **[Risk] `strict: true` may surface hidden type errors in converted files** -> Mitigation: The project already has `strict: true` and `allowJs` (which skips strict checks for JS files). Converting to TS will enforce strict checks. Fix issues as they arise per file.
- **[Risk] Enzyme test compatibility** -> Mitigation: Enzyme types (`@types/enzyme`) are already installed. Tests should work unchanged after renaming `.spec.tsx` if needed (currently only one test file exists).
- **[Risk] Build output changes** -> Mitigation: The Babel build (`build-babel`) already handles `.ts/.tsx` extensions. Removing `.js/.jsx` from its input won't change output structure.
